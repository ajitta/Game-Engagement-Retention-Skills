## 0. 결론

**볼트 조사가 이 저장소에 주는 것은 "문장을 이렇게 고쳐 써라"가 아니라 "문구 변경을 가설로 다루고 재는 방법"이다.** 지금 스킬 본문의 문구를 바꿀 근거는 없다.

이유는 넷이다.

1. **볼트가 측정으로 받치는 것은 좁고, 조건이 멀다.** 문형 사이의 일반 순위는 입증되지 않았다. 측정된 것은 사용자 발화의 입장·확신 표지가 동조를 키운다는 것, 영어 예/아니오 질문의 "no" 쏠림, 페르소나가 사실 정확도를 올리지 못한다는 것, 위협·보상의 평균 효과가 없다는 것이다. 동조와 쏠림은 사용자 턴·영어에서 잰 값이고, 넷 모두 다른 모델에서 나왔다. 스킬 본문 층에서 문형을 바꿔 잰 볼트 자체 실험은 없다. 금지문 대 긍정문, 이유 유무, 강조 표지는 벤더 권고이거나 추론이다.
2. **볼트 가이드가 겨냥하는 표적이 이 저장소에 거의 없다.** `plugin/` 아래에 대문자 CRITICAL·MUST·NEVER·ALWAYS, 역할 부여, 위협·보상, 질문형·청유형 지시가 0건이다. 금지는 소문자 never이고, 공유 블록에서는 금지 표지가 든 문장 단위 45개 중 23개가 긍정문·평서문의 꼬리로 붙어 있다. 금지가 주절인 22개 가운데 문단 안까지 보아도 대안이 없다고 분명히 말할 수 있는 것은 1개다.
3. **본문 문구 수정이 fp·tp를 움직인 10회 기록은 없다.** 10회 A/B는 두 번뿐이고 둘 다 삭제 위주의 묶음이었으며 둘 다 구분되지 않았다. 3회 수준에서는 문구를 더하거나 고쳐 쓴 뒤 케이스가 움직인 기록이 양방향으로 있고(§3), 그중 하나는 10회에서 재현되지 않았다. 최신 판독(3.4.1)의 결론은 "No body change follows from this reading"이다.
4. **지금의 게이트는 큰 하락만 읽는다.** fp 58/60은 50/60 이하로, tp 27/30은 19/30 이하로 떨어져야 구분되고(양측 Fisher, α 0.05, 같은 크기의 두 arm), 상승은 어느 쪽도 구분되지 않는다. 문형 하나를 바꾼 효과가 그보다 작으면 10회 A/B로는 보이지 않는다.

그래서 수행 순서는 다음과 같다. S0–S4는 모델이 읽는 스킬 문구를 바꾸지 않고, 그중 S0–S3은 새 생성도 필요 없다.

| 단계 | 하는 일 | 스킬 문구 | 새 생성 |
|---|---|---|---|
| S0 | 전제 확인: 저장 전사·하네스의 현존, CI에서의 검사 동작 | 불변 | 없음 |
| S1 | 측정 장치 보수: 검사 스크립트, 기록 양식, 묵은 문서 | 불변 | 없음 |
| S2 | 계수: 저장 전사와 본문에서 누출·복제·불일치를 세고 실패 표를 만든다 | 불변 | 없음 |
| S3 | 채점기 위생: 판정 프롬프트를 한 건씩 고쳐 저장 전사로 재판정 | 불변 (채점기만) | 없음 (판정 호출은 든다) |
| S4 | 사용자 문형 탐침: 문형만 바꾼 프롬프트 쌍 | 불변 | 있음 |
| S5 | 본문 실험: 진입 조건을 채운 좁은 후보만 | **변경** | 있음. 기본값은 열지 않음(Q6) |

S5까지 가더라도 기록상 기대치는 "구분 안 됨"이다. 이 지침의 어떤 항목도 문구 변경이 출력을 좋게 한다고 주장하지 않는다.

조사 중에 문형과 무관한 결함 하나를 찾았다. `scripts/check-no-facts-in-skills.sh` 31행의 frontmatter 제거식이 GNU sed에서 본문 전체를 지워서, 이 스크립트의 패턴 규칙이 본문 0줄을 검사한다(S1-1). 이 기기에서 재현했고, CI에서의 동작은 확인하지 못했다. **2026-10-03 수정함**(소유자 요청): 제거식을 한 번으로 줄였고, 스크립트가 머리말의 음성 시험(2줄을 더해 10줄)을 스스로 돌린다. 아래 S0-2, S1-1, Q8의 해당 부분은 닫혔다.

## 1. 근거 표지와 분류

근거는 강한 순서로 일곱 표지를 쓴다. 한 항목에 표지가 둘 이상 붙으면 가장 약한 표지가 그 항목의 등급이다.

| 표지 | 뜻 |
|---|---|
| 〈프로젝트 10회〉 | 이 저장소의 케이스당 10회 A/B·게이트 판독 |
| 〈프로젝트 3회〉 | 이 저장소의 3회·5회 판독. 스모크 수준이라 가설로만 쓴다 |
| 〈볼트 자체〉 | 볼트의 자체 실험(화행 검증 36회, 앵커링 검증 조건당 1회 등). 파일럿 규모 |
| 〈외부 측정〉 | 볼트가 기록한 외부 연구. 대부분 영어이고 초록 수준으로 읽은 것 |
| 〈안내〉 | 벤더 문서의 권고. 구절마다 대상 모델 세대가 다르다 |
| 〈추론〉 | 위 근거를 엮은 해석, 다른 층으로의 이전 |
| 〈미검증〉 | 근거를 찾지 못함. 크리에이터 일화는 여기에 들고 규칙의 근거로 쓰지 않는다 |

모든 수행 항목은 넷 중 하나로 분류한다. 글자만 쓰면 다른 번호와 헷갈리므로 항상 "분류 A"처럼 적는다.

| 분류 | 조건 |
|---|---|
| 분류 A — 측정 없이 가능 (확인 후) | 스킬 문구가 바뀌지 않고 새 생성도 없다. 저장 전사 재판정으로 확인하는 채점기 수정이 여기에 든다. "확인 없이 해도 된다"는 뜻이 아니다. 저장 전사가 남아 있다는 전제(S0-1)가 깨지면 분류 B가 된다 |
| 분류 B — 새 생성으로 측정 | 문구 변경 또는 프롬프트 탐침. 대조 arm을 같은 세션에서 케이스당 10회 이상 돌린다. 문구 변경은 그 문구를 읽는 eval 가족에 10회 기준선이 있을 때만 분류 B다 |
| 분류 C — 보류 | 그 문구가 읽히는 eval 가족에 10회 기준선이 없거나 근거가 얇다 |
| 분류 D — 비적용 | 대상이 이 저장소에 없거나, 저장소의 측정 기록·결정과 반대다 |

볼트 방향과 저장소 기록이 부딪히면 저장소 기록을 기본값으로 두고 §8의 결정 사항으로 올린다.

## 2. 철학과 컨셉

볼트 조사에서 살아남아 이 저장소에서도 성립하는 작업 원칙이다. 원칙은 문구를 바꾸지 않으며, §4 이후의 개별 항목을 거르는 기준으로만 쓴다.

**P1. 문형 순위표는 세울 수 없다. 네 축을 따로 본다.** 문법 형태(평서·의문·명령), 요청 기능(실행·판정·허락), 논리 구조(부정·조건), 확신·강조 표지는 서로 다른 축이다. 문장마다 먼저 "실행 지시인가, 판정 기준인가, 맥락 진술인가, 경계인가"를 정한다. 〈외부 측정〉 구형 모델에서는 질문·명령이 평서문보다 대체로 유리했지만 질문과 명령 사이에 일관된 승자가 없었고(Leidinger 2023), 평서문과 명령문의 순위는 모델에 따라 뒤집혔다(RCScore 2025, MATH-500). 볼트의 표현은 "순위가 없다기보다, 입증되지 않았다"이다. 네 축 분리 자체는 〈추론〉.

**P2. 프롬프트는 명령이 아니라 답 분포에 거는 조건이다.** 본문의 각 줄은 사실, 독자, 비목표, 완료 기준, 예시, 이유 중 하나로서 무언가를 좁히고, 좁히지 않은 자리는 모델의 기본값이 채운다. 〈추론〉

**P3. SKILL.md에 적은 것은 부탁이다.** 매번 지켜져야 하고 기계로 판정할 수 있는 규칙은 문형을 다듬지 않고 스크립트·채점기로 옮긴다. 〈안내〉는 CLAUDE.md에 대한 문서 서술(유저 메시지로 전달되고 준수 보장이 없다)이고, SKILL.md로 옮기는 것은 〈추론〉이다. 이 저장소의 실행 층은 CI와 채점기뿐이고 사용자 세션의 출력을 막지는 않는다. "실행 층으로 옮기면 준수율이 오른다"는 측정은 볼트에 없다.

**P4. 지시는 삭제로 갱신하고, 더하는 것은 되풀이된 실패에만.** 본문 길이는 "원하는 결과 − 지시 없이 나오는 결과"가 정한다. 〈프로젝트 10회〉 삭제 위주의 묶음 두 건이 구분되지 않았다. 반대 방향 기록도 있다: 표·행·예시를 지우거나 고쳐 3/3 → 0/3이 된 사례가 세 건이다(〈프로젝트 3회〉). 그러므로 삭제도 측정 없이 하지 않는다.

**P5. 형용사와 태도어는 결정 축을 지정하지 못한다.** 규칙은 "주의하라"가 아니라 "이 조건이면 쓴다 / 쓰지 않는다"나 셀 수 있는 칸으로 적는다. 〈추론〉

**P6. 판정은 작성 주체 밖에 둔다. 문구 효과에 대한 설명과 예측은 가설이다.** 〈볼트 자체〉 화행 검증에서 사전 등록한 예측 가운데 6–7건이 반증됐다. 이 지침이 내는 변경 제안(§5, §7)도 전부 후보와 측정 계획으로 적는다. §4.1의 작성 기준은 변경 제안이 아니라 새 문장을 쓸 때의 관례다.

**P7. 같은 설정의 반복 편차를 먼저 재고 나서 설정 간 차이를 읽는다.** 〈볼트 자체〉(계산) 10회 중 7과 8은 Fisher p = 1.0이고, 70%와 80%를 가르려면 조건당 약 293회가 든다(α 0.05, 검정력 0.8, 정규 근사). 〈프로젝트 10회〉 SKILL.md는 바이트 동일했지만 세션, Claude Code 버전, 페이로드 경로, 참조 모듈 5개가 달랐던 3.3.0과 3.3.1 사이에서 tp가 11/30 → 23/30(p 0.0038)이었고, 그중 무엇이 원인인지는 분리되지 않았다.

**P8. 측정한 현상은 이웃 현상의 증거가 아니다.** 동조 감소는 정확도 향상이 아니고, 스킬 발동률은 답의 질이 아니며, 계약 형식 준수는 유용함이 아니다. 사용자 턴에서 잰 결과를 스킬 본문이나 판정 프롬프트로 옮기면 〈추론〉이 된다. 모델도 같다: 이 지침의 모든 판독과 §4.3의 동결 근거는 claude-opus-5-5와 기록된 Claude Code 버전에서 잰 것이다. 게이트 모델이나 버전이 바뀌면 문구를 바꾸지 않았어도 기준 arm을 다시 돌리고, 이전 판독은 새 모델의 근거로 쓰지 않는다(Q17).

**P9. 모델이 읽는 문자열은 모델이 쓰는 문자열이 된다.** 예시 값은 앵커, 형식은 프레임이다. 〈프로젝트 3회〉 계약 예시의 영문 `Basis:` 라벨이 한국어 답에 복제됐고 예시에서 빼자 0이 됐다. 〈프로젝트 10회〉 금지 문장이 있는데도 3.4.1 fp 60회 중 1회가 Basis에 슬러그를 적었다. frontmatter 예시는 반대로 라우팅을 일으키는 문구라 줄일 수 없다.

**P10. 측정된 스킬의 값은 측정 방법론 쪽에 있었다.** 〈볼트 자체〉 실험 4는 retention-strategy-designer 한 스킬, 과제 1종, 스킬군 6 대 사후에 더한 호출 금지 통제군 3, Sonnet, 비맹검이다(스킬 버전은 노트에 없고 날짜상 2.0.0 이전으로 추정). 방법론 5항목 중 3항목이 6/6 대 0/3, 2항목이 6/6 대 1/3이었고 제안 내용은 비슷했다. 문형 수정은 return event·지표 규약·Measure·Kill if 같은 항목이 빠지지 않는지로 평가한다. 다른 두 스킬과 현행 3.4.1로 옮기는 것은 〈추론〉이다.

### 4.2 새로 넣지 않는 것

대상이 지금 0건이므로(인용된 제품 문구와 HTML 주석 마커는 제외) "0건을 유지한다"가 규칙이다.

- 대문자 CRITICAL·MUST·NEVER·ALWAYS, 지시문의 느낌표, 위협·보상·벌칙 어조. 〈안내〉(Opus 4.5·4.6의 도구·스킬 과소 발동 보정 문구가 대상) + 〈외부 측정〉 위협·보상의 평균 효과 없음.
- 새 강제 발동 문구. RSD when_to_use의 `run this even when a direct answer looks easy — its bounds are looked up, not recalled`는 3회 기록이 있는 기존 문구이므로 그대로 둔다.
- 전문가 페르소나 문장(SKILL.md 서두, 모듈 머리말, judge 호출). 〈외부 측정〉 사실 정확도 이득 없음. "역할은 해롭다"의 근거로 쓰지는 않는다.

### 4.3 바꾸지 않는 것

### 6.1 실험 설계

저장소가 이미 하는 것은 다시 제안하지 않는다: 케이스당 10회 이상, Wilson 95% 하한 ≥ 80%, 개수 옆 Fisher p, 전사마다 별도 judge 호출, 저장소 밖 실행, 3회 결과로 규칙 추가 금지, 채점기를 고치면 저장 전사 재판정. 아래는 그 위에 얹는 것이다. 양식으로 적어 두는 일은 분류 A이고, E2의 A′ arm, E15, E16을 실제로 돌리는 것은 새 생성이라 분류 B다(Q15). CONTRIBUTING의 규칙 문구를 바꾸는 것은 Q18이다.

### 6.2 채점기(판정 프롬프트) 위생

`type: llm_judge` 채점기 36개는 모델에게 보내는 프롬프트이고, 저장소 기록상 채점기 문구만 바꿔도 같은 전사의 점수가 움직였다. 볼트의 동조·쏠림 측정은 사용자 턴이 대상이라 판정 프롬프트로 옮긴 주장은 모두 〈추론〉이다. 그래서 아래는 전부 재판정 계획이 붙은 가설이다. 한 건씩 고치고, 본문 두 버전 이상의 저장 전사로 재판정하며, tp와 fp를 함께 본다.

저장소의 현행 기준은 "채점기는 계약에 없는 것을 요구하거나 내부 모순일 때만 고친다"이다. 이 기준 안에 드는 것은 J1, J3, J4, J10–J12이고, J5–J9는 그 기준을 넘으므로 Q4에서 허용한 경우에만 한다.

1. **J1 실제 judge 호출 래퍼 확보.** 저장소 안에 적힌 래퍼(채점기와 전사를 끼워 보내는 틀)는 `evals/README.md:279-288`뿐인데, 3.4.1 하네스는 `prompt.md`도 judge에게 넘긴다. README 래퍼를 실제 호출과 같게 고친다.
2. **J2 손 라벨 기준 세트** (Q14). 생성과 판정이 같은 모델이고 사람 판정과 대조한 기록이 없다. fp·tp 저장 전사에서 소표본을 손으로 항목별 라벨해 judge와의 일치율을 잰다. 게이트 수치는 "judge 기준 통과율"로 부른다.
3. **J3 재판정 절차 명문화.** 채점기 수정 한 건마다 옛 판정 대 새 판정의 2×2 일치표와 뒤집힌 항목 번호를 적는다.
4. **J4 계약과 채점기의 불일치 정리.** Basis 길이(계약 "one line", `ending.md` "at most two non-empty lines", hidden-odds "one or two sentences"), `## 측정 설계` 대 `## 측정 계획`, 폐기된 "6/6 across the family" 문구. Basis 길이는 어느 쪽을 정본으로 할지가 Q5이고, 계약 쪽을 고치는 것은 본문 변경이라 S5로 간다.
5. **J5 유지보수자 문장과 덮어쓰기 층** (Q4). 버전 이력 "(3.2.0) … The skill now names …" 23개 파일, "This supersedes any wording above" 6개 fp 파일, `With-only`·`Scored, both arms` 행. 최종 규칙만 남긴 판으로 재판정한다.
6. **J6 기대 결론과 케이스 의도** (Q4). "A true positive:", "Release gate", "tempting", 스킬 없는 arm의 행동 예상 문장. 판정에 필요한 사례 사실은 남기고 의도·예상 서술만 뺀 판으로 재판정한다. 사례 사실까지 지우면 fp의 침묵 항목을 판정할 근거가 없어진다.
7. **J7 전체 판정을 코드로 계산** (Q4). judge에게는 항목별 판정만 받고 전체 판정은 항목에서 계산한다. 번호 밖 FAIL 조건에는 번호를 준다.
8. **J8 판정 유보 값** (Q4, Q11). 항목별 값에 UNDETERMINED를 더해 따로 센다. 유보율 상한을 실행 전에 적는다.
9. **J9 항목별 근거 인용 뒤 판정** (Q4). PASS 항목에도 같은 형식을 요구한다. 인용된 줄이 실제 전사에 있는지 문자열로 검사한다.
10. **J10 스크립트로 셀 수 있는 기준의 이관.** `ending.md` 3개는 본문이 스스로 "A check a script could run"이라 적는다. 슬러그·티어 코드·`Mode:` 누출, 섹션 순서, 표 열 수도 후보다. 헤딩·라벨은 "기능으로 채점"이라 문자열 일치로 옮길 수 없다. 스크립트로 옮긴 항목을 judge 통과 조건에서 빼면 통과율이 올라 보이므로 스크립트 점수를 같은 표에 적는다. 게이트 가족에는 새 스크립트 조건을 통과 조건으로 더하지 않고 별도 열로만 센다.
11. **J11 경계 문장과 닫힌 목록.** 일상어와 내부 키를 가르는 문장이 fp 6개 중 1개(`fp-companion-checkin-user-cadence/graders/criteria.md:26`), mode-line 10개 중 1개(`homeless-rolling-vs-classic/graders/mode-line.md:9`)에만 있고, fp 채점기의 슬러그 목록이 파일마다 다르다. 같은 가족 전 파일에 같은 문장·같은 목록을 둔 판으로 재판정한다.
12. **J12 채점되지 않는 단언.** `routing-edge-session-length/graders/skill-fired.md:11`과 `homeless-arpdau-vs-d7/graders/skill-fired.md:13`의 내용 단언은 Skill 호출을 세는 tool_use 채점이 보지 않는 것으로 보인다. llm_judge 채점기로 옮길지 지울지는 소유자가 정한다(옮기면 가족 문턱이 바뀐다).

하지 않는 것: FAIL 극성을 PASS 쪽으로 전면 고쳐 쓰기(근거가 유추뿐), 공통 단락의 별도 파일 분리(프로젝트 기록이 비추천). 인용된 금지 문자열은 판정 프롬프트에서 생성 앵커가 아니라 검출 키이므로 생성용 규칙(R7)을 여기에 옮기지 않는다.

### 6.3 eval 프롬프트의 공백과 문형 탐침

39개는 39개의 서로 다른 시나리오이고 문형만 바꾼 쌍이 0이라, 이 스위트로는 사용자 문형이 스킬 동작을 바꾸는지 잴 수 없다. 게이트 수치(fp 58/60, tp 27/30)는 사실상 "정해진 설계 서술 + 실행 요청"이라는 한 문형 조합에서 잰 값이다.

기존 프롬프트는 고치지 않는다(작성 뒤 한 번도 수정되지 않았고, 고치면 기존 수치와 비교할 수 없다). 시나리오·사실·요청 종류를 고정하고 사용자 쪽 손잡이 하나만 바꾼 변형을 짝으로 두는 **게이트 밖 탐침**을 둔다.

| 쌍 | 바꾸는 것 | 기준 케이스(제안) | 볼 것 | 분류 |
|---|---|---|---|---|
| U1 | 명령형 ↔ 질문형 요청 ("Build me …" ↔ "Can you build …?") | refusal-tp-ad-chaining, fp-stamina-published-refill | 거절·침묵 동작이 유지되는가 | 분류 B |

| U3 | 한국어 트리거 낱말 그대로 ↔ 같은 시나리오를 그 낱말 없이 | korean-routing 3케이스 | 낱말 일치인가 의미 라우팅인가 | 분류 B |

채점은 U1·U2에서 기준 케이스의 채점기를 그대로 쓴다. U3·U5는 Skill 호출을 세는 방식(맞는 스킬 / 다른 스킬 / 미발동)으로 보고 답의 내용은 보지 않는다. U4는 기준 케이스의 채점기가 "묻고 멈춘다"를 요구해 그대로 쓸 수 없으므로 변형 arm용 항목 셋(질문 0개, `[assumed]` 4줄 이하, "물을 수 없었다"는 메모 없음)을 사전 등록에 적고 스크립트로 센다. U8은 항목 수를 스크립트로 센다.

작성 규칙: 요청 종류(실행·판단)를 바꾸지 않는다. 표지만 더하고 프롬프트가 준 사실은 그대로 둔다. 의문형 변형이 read·compare 모드를 부르면 그 쌍은 문형이 아니라 모드 규칙을 잰 것으로 적는다. 변형이 frontmatter 예시와 겹치는지 케이스마다 적는다.

쌍 하나는 2 arm × 10회 = 생성 20회, 약 $13–14다. 최소 구성(U1 2쌍, U2 3쌍, U3 3쌍, U4 1쌍, U5 4칸, U8 1쌍)은 생성 240회, 환산 약 $152–165이고 판정 비용은 별도다(Q15). 탐침이 보여 줄 수 있는 것은 10/10 대 5/10 이하 같은 큰 붕괴뿐이다. 그런 결과가 나오면 S2-5 실패 표에 "사용자 문형 조건"으로 올리고 한 번 더 돌려 재현을 본다. 탐침의 수치로 본문에 문장을 더하지 않는다. 변형 프롬프트를 `evals/` 아래에 케이스로 넣으면 `check-claims.sh`의 "39 cases"와 게이트 분모가 달라지므로 위치는 Q10이다.

1. 변경 arm을 채택하기 전에 게이트 밖 30케이스를 변경 본문으로 케이스당 3회 돌린다(스모크, 약 90회). 이전 기록에서 통과하던 케이스가 0/3이 되면 출하하지 않고 그 케이스를 변경 전 본문과 같은 세션에서 10회씩 대조한다. 3회 스모크의 통과는 "회귀 없음"의 증거가 아니라는 점을 판독에 적는다. 3.4.0이 fp·tp 비열등으로 출하된 뒤 mode 케이스가 3/3 → 0/3이었던 것이 이 절차가 막으려는 모양이다.
2. 바꾸는 문장을 인용하는 채점기를 grep으로 먼저 찾는다. 채점기를 함께 고쳐야 하면 그 수정을 S3 절차로 먼저 재판정해 기록한 뒤 동결하고, 그다음에 본문 A/B를 돌린다.
3. 문구를 바꾸는 변경은 같은 커밋에서 버전을 올리고 CHANGELOG에 "어느 스킬이 다르게 발동하는지"를 적는다. 공유 블록은 `scripts/contracts.md`와 세 SKILL.md를 같은 바이트로 고친다. 출하는 `scripts/release.sh`로 하고 토큰을 다시 재서 README 표에 적는다.
4. 되돌림은 변경 전 바이트로의 복원이며 "복원"으로 표시한다. 복원을 3회 스모크로 출하할 수 있는지는 Q18이다.

10회 기준선이 없는 표면(ROUTING, LANGUAGE, Modes 행, Intake, frontmatter, 게이트가 읽지 않는 모듈, 블록 순서)은 S5의 대상이 아니다. 기준선을 만들지는 Q7이다.

## 9. 이 지침이 기대지 않는 주장

볼트가 스스로 철회하거나 좁혔거나, 근거를 찾지 못한 것들이다. "틀렸다"가 아니라 "여기에 기대지 않는다"는 뜻이다. 볼트의 표현대로 근거 미확보는 효과 없음의 증명이 아니다.

| 주장 | 볼트의 판정 | 이 저장소에서 |
|---|---|---|
| 질문형·요청형으로 바꾸면 더 정확해진다 | 근거 부족. 줄어든 것은 동조이고 동조는 정확도의 대리 지표가 아니다 | 질문형 지시 0건. 분류 D |
| `Let's`(청유형)가 효과의 원인이다 | 불일치. 효과는 함께 들어간 단계 지시에서 왔다 | 청유 문장 0건. 분류 D |
| 위협·보상·팁이 성능을 올린다 | 평균 효과 없음(Wharton 보고서 3, 초록 수준). "위협이 사고 자원을 늘린다"는 확인 불가 | 0건. 분류 D |
| 강조 단어를 반복하면 지켜진다 | 볼트에 측정 없음. 구형 모델 대상 목록에서 온 주장 | 0건. 분류 D |
| 전문가 페르소나가 정확도를 올린다 | 축소. 정확도 이득 없음, 정렬 이득은 소형 모델 한 편 | 역할 줄 0건. 넣는 것도 "역할 금지"를 적는 것도 하지 않는다 |
| 조동사를 고정하면 강도가 조절된다 | 축소. 근거는 의문문 속 조동사 비교였고 드러난 것은 불안정성이다 | must·should·may 혼용이 거의 없다. 분류 D |
| 조건문은 항상 성능을 낮춘다 | 근거 부족 | 조건부 규칙을 문형 이유로 고치지 않는다 |
| 추론 모델에 단계별 사고를 지시한다 | 추론 모델에서는 이득이 거의 없다 | 0건. 분류 D |
| 끝내기 전에 검증하라는 지시를 넣는다 | Opus 5 가이드 기준으로 무효 선언(effort 조건 없음). Sonnet 5.5 문서는 낮은 effort에서 넣으라고 해 볼트 안에서 풀리지 않았다 | `Reread before sending`은 셀 수 있는 조건의 점검 목록이고 동결 목록에 있다. 이 철회만으로 지우지 않는다 |
| 금지문은 역효과이니 긍정문으로 바꾼다 | 미검증. 세션 결론은 "중요한 금지는 유지, 가능하면 대체 행동"으로 좁혔다 | never의 일괄 변환은 분류 D |
| 시스템 프롬프트의 "NEVER do X"를 서술형으로 바꾸면 분산이 81% 준다 (Mason 2026) | 시스템 프롬프트 층에서 문형(명령형 대 서술형)을 대비한 것으로 볼트가 기록한 유일한 주장. 단독 저자, 초록 요약 수준 | 〈미검증〉으로 두고 규칙 근거로 쓰지 않는다 |
| 맹점 탐색 통합 프롬프트는 검증됐다 | 미검증. 문헌 기반 설계이고 직접 시험하지 않았다 | 해당 블록 없음. 분류 D |

| 가드레일 언급이 스킬 효과의 지표다 | 철회. 통제군 3/3도 가드레일을 냈다 | 현행 계약은 준수하는 메커닉에 침묵이 정답이다 |
| 크리에이터 수치(40–60% 절감, 50 → 95점) | 일화 | 감축 비율을 목표로 삼지 않는다. Anthropic 강연의 시스템 프롬프트 80% 감축은 보도 기준 확인이지만 감축의 효과는 미측정이다 |
